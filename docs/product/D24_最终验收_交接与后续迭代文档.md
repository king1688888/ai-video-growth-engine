## 2. 文档目标

### 2.1 本文档要解决的问题

D24 要解决的是 AIcoding 多模块研发完成后最容易失控的最后一公里问题：单个模块看似完成，但整体项目无法上线、无法收费、无法运维、无法交接、无法继续迭代。

本项目不是普通 CRUD SaaS，而是包含视频上传、多模态理解、Content DNA、Creative IR、Prompt Registry、模型路由、异步任务、文件资产、积分计费、相似度风控、AIGC 标识、人工复核、投诉删除、运营后台、测试发布监控的商业级 AI 产品。D24 必须把这些能力从“各自完成”聚合成“整体可交付”。

D24 必须解决以下 12 个问题：

1. **最终验收如何判定**：明确 MVP1 是否达到可内测、可灰度收费、可正式上线的证据标准。
2. **模块交付如何收口**：每个模块必须有代码、测试、接口、日志、异常、权限、文档、风险和未完成项说明。
3. **AI 能力如何验收**：Content DNA、Creative IR、Prompt 输出、质量评分、风控拦截必须有 Schema、Prompt 版本、Benchmark、失败回退和质量阈值。
4. **工程能力如何验收**：数据库迁移、API 契约、任务队列、对象存储、日志、权限、CI/CD、监控、告警、回滚必须可执行。
5. **商业化如何验收**：积分预估、冻结、扣费、返还、订单、模型成本、毛利统计、后台补偿、退款审计必须闭环。
6. **合规如何验收**：授权确认、AIGC 标识、风险分级、拦截策略、人工复核、投诉删除、审计日志必须可验证。
7. **上线前如何决策**：定义 Go / Conditional Go / No-Go / Rollback 的决策规则和签署责任。
8. **交接如何执行**：定义研发交接、运维交接、Prompt 交接、运营交接、客服交接、合规交接的资产包。
9. **已知问题如何管理**：区分 P0 阻断、P1 必修、P2 可排期、P3 观察，避免带病上线。
10. **后续迭代如何治理**：任何新增能力必须经过需求、Schema、API、Prompt、风控、成本、测试和发布影响评估。
11. **AIcoding 如何收尾**：输出可直接交给 Manus / Codex / Claude Code / Hermes Agent 的最终验收与交接任务提示词。
12. **如何防止后续返工**：通过版本冻结、契约锁定、变更控制、Runbook、交接记录和验收证据减少上下文丢失。

## 4. 核心结论

### 4.1 D24 的一句话结论

MVP1 只有在「产品范围正确、AI 输出可验证、工程链路可运行、异步任务可恢复、积分计费可审计、合规风控可拦截、运营后台可处理、发布监控可告警、交接资产可维护」全部具备证据后，才允许从 AIcoding 研发状态进入内测、商业化灰度或正式生产。

### 4.2 最终验收不是看页面，而是看证据链

最终验收必须基于以下证据链，而不是基于截图、演示或 Agent 自述：

```text
需求文档
→ 模块边界
→ 数据库迁移
→ API 契约
→ 任务状态机
→ Prompt Registry
→ 模型调用日志
→ AI Benchmark
→ 风控报告
→ 积分交易流水
→ 测试报告
→ 监控告警
→ 运营工单
→ 合规审计
→ 交接记录
```

### 4.3 MVP1 上线必须满足 11 类最终门禁

| 门禁编号 | 门禁名称 | 阻断条件 |
|---|---|---|
| G0 | 文档一致性门禁 | D00-D23 存在未解决的 P0 冲突，或 D16/D17/D19/D21/D20 口径未统一 |
| G1 | 产品范围门禁 | 主流程出现搬运、克隆、洗稿、仿脸、仿声、自动抓取、自动发布等超范围能力 |
| G2 | 工程真实能力门禁 | P0 主链路依赖未标记 mock，或无真实数据库/API/队列/日志 |
| G3 | AI 质量门禁 | Content DNA / Creative IR / 输出包无法通过 Schema、Benchmark、人工抽检或风控检查 |
| G4 | 异步任务与资产门禁 | 长任务不可追踪、不可重试、不可补偿、资产不可删除或越权访问 |
| G5 | 商业化计费门禁 | 积分冻结/扣费/返还不幂等，模型成本无法归因，失败无法补偿 |
| G6 | 合规风控门禁 | 授权、AIGC 标识、风险分级、拦截、人工复核、投诉删除任一 P0 缺失 |
| G7 | 安全权限门禁 | 用户资产、后台数据、模型日志、密钥或支付数据存在越权/裸露风险 |
| G8 | 测试发布门禁 | 单元/API/E2E/队列/Prompt/风控/计费/权限/Smoke 任一 P0 不通过 |
| G9 | 运营交接门禁 | 后台、工单、客服补偿、人工复核、Runbook、值班责任不完整 |
| G10 | 可维护性门禁 | 无启动命令、部署说明、回滚方案、已知问题清单、维护 Owner 或文档索引 |

### 4.4 Go / Conditional Go / No-Go 判定

| 决策 | 适用条件 | 可执行动作 |
|---|---|---|
| Go | 所有 G0-G10 P0 门禁通过；无 P0/P1 阻断问题；P2 有明确排期 | 允许进入目标阶段，如内测、灰度收费或正式生产 |
| Conditional Go | 无 P0；存在少量 P1，但有临时规避、Feature Flag、监控和 Owner | 允许小范围内测或灰度，不允许大规模商业化放量 |
| No-Go | 存在任一 P0 阻断，或合规/计费/安全/AI 高风险未解决 | 禁止上线，必须回到研发修复 |
| Rollback | 发布后出现 P0 事故、合规事件、资金异常、数据泄露、AI 高风险输出 | 立即回滚或关闭相关 Feature Flag，进入事故响应 |

### 4.5 D24 对后续迭代的核心判断

MVP1 上线后，后续迭代不能按“想到什么做什么”推进，而必须进入版本治理：

```text
用户反馈 / 运营问题 / 数据诊断 / 商业化需求 / 合规事件
→ 迭代候选
→ 影响评估
→ 文档回写
→ Schema/API/Prompt/风控/成本评估
→ AIcoding 任务拆分
→ 测试与验收
→ 灰度发布
→ 复盘回写
```

任何影响数据库、API、任务状态、积分计费、AI Prompt、风控合规、权限安全的变更，都必须走变更控制，不允许后续 Agent 直接改代码上线。

## 5. 详细设计

### 5.1 最终验收范围

D24 验收的 MVP1 范围如下：

```text
用户注册/登录
→ 用户画像 Onboarding
→ 视频上传 / 链接输入
→ 授权确认
→ 积分预估与冻结
→ 视频处理：元数据、抽帧、ASR、OCR、镜头切分
→ 多模态证据包
→ Content DNA 生成
→ 拆解报告生成
→ Creative IR 原创化重构
→ 原创脚本 / 标题 / 封面建议 / 视频 Prompt 输出
→ 质量评分与相似度风控
→ 合规审核与 AIGC 标识
→ 结果页展示与导出
→ 任务历史
→ 成功扣费 / 失败返还 / 部分成功结算
→ 后台任务诊断 / 成本统计 / 人工复核 / 客服工单
→ 测试、监控、告警、回滚、交接
```

MVP1 不验收以下能力作为上线必要条件：账号级全量抓取、自动发布、完整视频生成平台、团队协作工作流、企业多组织复杂权限、自动数据抓取、自动 Prompt 替换上线、跨平台自动运营、仿脸、仿声、原视频风格复制、下载搬运、规避平台审核。

### 5.2 最终验收分层

| 层级 | 验收对象 | 通过标准 |
|---|---|---|
| L1 文档验收 | D00-D23 与 D24 | 文档编号、边界、依赖、字段、状态、风控、计费无 P0 冲突 |
| L2 模块验收 | 前端、后端、AI、队列、计费、风控、后台 | 每个模块都有 ModuleHandoffRecord、测试证据、API/Schema 证据 |
| L3 集成验收 | MVP1 主链路 | 用户从上传到结果到扣费/返还的链路跑通，异常可恢复 |
| L4 AI 质量验收 | Content DNA、Creative IR、输出包、风控 | Schema 合法、Benchmark 达标、人工抽检通过、风险可拦截 |
| L5 商业化验收 | 套餐、积分、订单、成本、毛利 | 交易幂等、成本可归因、失败可返还、后台可统计 |
| L6 合规安全验收 | 授权、AIGC、审核、权限、删除 | 高风险可阻断，用户数据可删除，后台访问可审计 |
| L7 发布运维验收 | CI/CD、环境、监控、告警、回滚 | 可部署、可监控、可告警、可回滚、可 Smoke |
| L8 运营交接验收 | 后台、客服、人工复核、Runbook | 运营能处理失败、投诉、退款、复核和补偿 |
| L9 版本治理验收 | 迭代候选、变更控制、后续 Owner | 后续维护不会丢失上下文，不会无序扩展 |

### 5.3 最终验收流程

#### 5.3.1 阶段 1：版本冻结

输入：

- 当前 Git 分支和 Commit Hash。
- 数据库迁移版本。
- Prompt Registry 版本。
- 模型路由配置版本。
- 风控规则版本。
- 套餐积分配置版本。
- 部署环境配置版本。

处理规则：

1. 冻结目标版本，形成 `ReleaseCandidate`。
2. 禁止非阻断修复直接进入候选版本。
3. 所有后续变更必须关联 `change_request_id`。
4. 文档、代码、迁移、Prompt、配置必须打同一批次版本标签。

输出：

- `release_candidate_id`。
- `version_tag`，例如 `mvp1-rc.1`。
- 版本冻结说明。
- 变更窗口与责任人。

#### 5.3.2 阶段 2：证据收集

输入：

- 模块交付记录。
- 自动化测试报告。
- AI Benchmark 报告。
- Prompt 回归报告。
- 风控红队报告。
- 计费幂等报告。
- 安全权限测试报告。
- 监控告警配置。
- Runbook。
- 已知问题清单。

处理规则：

1. 每一项证据必须绑定模块、Commit、环境、时间、执行人或 Agent。
2. 证据不得只使用自然语言描述，必须包含可复现命令、截图、日志、报告文件或系统记录。
3. 失败证据不得删除，必须记录失败原因、修复记录和复测结果。
4. 所有高成本 AI 测试必须记录模型调用和成本。

输出：

- `AcceptanceEvidenceItem[]`。
- `AcceptanceGateResult[]`。
- 缺失证据列表。

#### 5.3.3 阶段 3：自动门禁检查

自动检查内容：

1. 数据库迁移是否可在空库和已有库执行。
2. API 合约测试是否通过。
3. 队列任务状态是否完整。
4. 对象存储访问权限是否正确。
5. Prompt 输出是否通过 JSON Schema。
6. Benchmark 是否达到门槛。
7. 风控红队样本是否拦截。
8. 积分冻结/扣费/返还是否幂等。
9. 后台权限是否防越权。
10. CI/CD、预发部署、Smoke 是否成功。
11. 监控和告警是否已配置。

输出：

- `auto_gate_passed: true/false`。
- 自动门禁失败项。
- 阻断等级和 Owner。

#### 5.3.4 阶段 4：人工复核与签署

人工复核角色：

| 角色 | 签署范围 |
|---|---|
| 产品负责人 | MVP1 范围、页面流程、用户价值、已知问题是否可接受 |
| 技术负责人 | 架构、数据库、API、队列、部署、回滚、技术债 |
| AI 负责人 | Prompt、模型路由、Benchmark、质量、失败回退 |
| 测试负责人 | 测试覆盖、缺陷状态、发布门禁、回归计划 |
| 商业化负责人 | 积分、订单、扣费、返还、成本、毛利、补偿 |
| 合规负责人 | 授权、AIGC 标识、审核、投诉删除、人工复核 |
| 运营负责人 | 后台、客服、工单、补偿、用户通知、SOP |
| 项目 Owner | 最终 Go / Conditional Go / No-Go 决策 |

签署规则：

1. 合规、安全、计费任一负责人拒签，则不得商业化上线。
2. 技术负责人拒签，则不得生产发布。
3. 测试负责人拒签，则不得进入下一阶段。
4. 项目 Owner 可以批准 Conditional Go，但必须记录限制范围、监控指标、回滚条件和截止修复日期。

#### 5.3.5 阶段 5：交接执行

交接内容：

1. 仓库与代码结构。
2. 环境与部署。
3. 数据库迁移。
4. API 文档。
5. 队列与 Worker。
6. Prompt Registry。
7. 模型供应商和成本配置。
8. 风控规则和人工复核。
9. 积分与订单。
10. 后台与客服。
11. 监控告警与事故响应。
12. 已知问题与后续迭代。

交接输出：

- `HandoffPackage`。
- `RunbookIndex`。
- `KnownIssueRegister`。
- `IterationCandidateBacklog`。
- `OwnershipMap`。

### 5.5 缺陷等级与上线影响

| P3 观察 | 优化项、体验项、后续增强 | UI 微调、非核心指标图表 | 不影响上线 |

### 6.5 Prompt 设计

D24 本身不新增面向普通用户的高成本创作 Prompt，但可以使用 AI 辅助完成验收证据审阅、交接摘要、已知问题分级和迭代影响分析。所有 D24 Prompt 必须纳入 Prompt Registry，记录 PromptRun、模型、成本、输入输出、版本和人工复核结果。

#### 6.5.1 P24_ACCEPTANCE_EVIDENCE_REVIEW

用途：审阅验收证据是否完整，识别缺失证据、冲突、阻断风险。

输入 Schema：

```json
{
  "package_id": "string",
  "target_stage": "internal_alpha | closed_beta | commercial_gray | production | hotfix",
  "gate_results": [
    {
      "gate_code": "string",
      "status": "string",
      "summary": "string",
      "evidence_refs": ["string"]
    }
  ],
  "evidence_items": [
    {
      "id": "string",
      "evidence_type": "string",
      "module": "string",
      "title": "string",
      "source_ref": "string",
      "is_reproducible": true
    }
  ],
  "known_issues": [
    {
      "id": "string",
      "title": "string",
      "severity": "P0 | P1 | P2 | P3",
      "status": "string",
      "impact": "string"
    }
  ]
}
```

输出 Schema：

```json
{
  "overall_readiness": "ready | conditional | blocked",
  "missing_evidence": [
    {
      "gate_code": "string",
      "missing_item": "string",
      "severity": "P0 | P1 | P2 | P3",
      "reason": "string"
    }
  ],
  "conflicts": [
    {
      "source": "string",
      "conflict": "string",
      "recommended_resolution": "string"
    }
  ],
  "blocking_risks": [
    {
      "risk": "string",
      "severity": "P0 | P1 | P2 | P3",
      "owner_role": "string",
      "next_action": "string"
    }
  ],
  "recommended_decision": "go | conditional_go | no_go | rollback",
  "decision_notes": "string"
}
```

质量标准：

- 必须覆盖 G0-G10 每个门禁。
- 不得把缺失证据误判为通过。
- 对合规、安全、计费问题必须保守判断。
- 输出必须可被 JSON Schema 校验。
- AI 建议仅作为辅助，不得替代人工签署。

失败回退：

1. JSON 解析失败：触发 JSON repair。
2. 缺少关键输入：返回 `blocked`，列出缺失字段。
3. 模型不确定：返回 `conditional` 或 `blocked`，不得默认 `ready`。
4. 模型调用失败：转人工验收，不影响真实证据保存。

#### 6.5.2 P24_HANDOFF_SUMMARY_GENERATION

用途：根据模块交接记录生成面向后续维护 Agent 的交接摘要。

输出必须包含：

1. 模块入口。
2. 代码文件。
3. API。
4. 数据库表。
5. 队列。
6. Prompt。
7. 测试命令。
8. 环境变量。
9. 常见故障。
10. 风险和未完成项。

禁止输出：

- 未验证的运行命令。
- 未确认的密钥。
- 绕过权限、风控、计费的操作建议。
- “大概可以”“应该可以”这类不可执行描述。

#### 6.5.3 P24_KNOWN_ISSUE_TRIAGE

用途：对已知问题进行 P0-P3 分级和上线影响判断。

分级规则：

- 涉及合规、安全、计费、数据丢失、主链路不可用、无法回滚：默认 P0。
- 涉及核心体验但有明确 workaround：P1。
- 不影响主流程且可排期：P2。
- 纯体验优化或观察项：P3。

输出必须包含：

- 问题等级。
- 是否阻断上线。
- 影响模块。
- 临时规避。
- 责任人角色。
- 修复版本。
- 回归测试建议。

#### 6.5.4 P24_ITERATION_IMPACT_ANALYSIS

用途：评估后续迭代候选对文档、Schema、API、Prompt、风控、计费、测试和部署的影响。

输出必须包含：

- 影响文档。
- 影响模块。
- 是否需要 D03 范围调整。
- 是否需要 D16 迁移。
- 是否需要 D17 状态变更。
- 是否需要 D10 Prompt 新版本。
- 是否需要 D12 Benchmark 更新。
- 是否需要 D13/D21 风控更新。
- 是否影响积分成本。
- 推荐版本和优先级。

### 6.7 状态机设计

#### 6.7.1 验收包状态

```text
draft
→ collecting_evidence
→ under_review
→ approved / conditional_approved / rejected
→ archived
```

异常分支：

```text
under_review → blocked → collecting_evidence
approved → rollback_required → archived
conditional_approved → expired_conditions → blocked
```

#### 6.7.2 门禁状态

```text
not_started
→ running
→ passed / warning / failed / waived
```

规则：

- P0 门禁不得 `waived`，除非项目 Owner、技术负责人、合规负责人三方共同签署，且只能用于非生产内测。
- 合规、安全、计费类 P0 不允许豁免进入商业化灰度或生产。
- `warning` 必须关联 KnownIssue。

#### 6.7.3 交接记录状态

```text
draft
→ submitted
→ reviewed
→ accepted / rejected
→ archived
```

拒绝原因必须具体到：缺代码入口、缺启动命令、缺测试证据、缺风险说明、缺 Owner、缺回滚说明、缺文档链接。

#### 6.7.4 迭代候选状态

```text
proposed
→ triaged
→ approved / rejected
→ scheduled
→ in_development
→ in_review
→ released
→ post_reviewed
```

任何 `approved` 进入 `scheduled` 前必须完成影响评估。

## 7. 异常与失败处理

### 7.1 最终验收异常矩阵

| 异常 | 识别方式 | 等级 | 处理策略 | 是否阻断 |
|---|---|---:|---|---|
| 缺少 P0 模块交接记录 | HandoffRecord 缺失 | P0 | 补齐交接记录和测试证据 | 是 |
| P0 主链路依赖未标记 mock | 代码审查 / 测试 / Agent 说明 | P0 | 替换为真实逻辑或显式关闭该能力 | 是 |
| 数据库迁移失败 | CI / 预发部署 | P0 | 修复迁移、增加回滚脚本、复测 | 是 |
| API 契约不一致 | Contract Test | P0/P1 | 以 D16 为准修复前后端 | 视影响 |
| 队列任务卡死 | 队列测试 / 监控 | P0 | 增加超时、重试、死信、补偿 | 是 |
| AI 输出 Schema 不合法 | Benchmark / 运行日志 | P0/P1 | JSON repair、Prompt 修复、模型回退 | 视比例 |
| AI 输出高相似或违规 | 风控红队 / 人审 | P0 | 强制重写、拦截、更新风控样本 | 是 |
| 积分重复扣费 | 计费幂等测试 | P0 | 修复幂等键和事务；回滚账务 | 是 |
| 失败未返还积分 | 补偿测试 | P0 | 修复补偿队列和交易状态 | 是 |
| 模型成本无法归因 | ModelCallLog 缺失 | P1/P0 | 补齐成本日志和任务关联 | 商业化阻断 |
| 授权确认缺失 | 合规验收 | P0 | 禁止任务创建，补授权流程 | 是 |
| AIGC 标识缺失 | 合规验收 | P0/P1 | 页面和导出补标识 | 商业化阻断 |
| 投诉删除不可执行 | 合规/运营演练 | P0 | 补删除链路、审计和通知 | 是 |
| 后台越权访问 | 安全测试 | P0 | 修复 RBAC/ABAC 和脱敏 | 是 |
| 监控告警缺失 | D20 门禁 | P1/P0 | 补指标、告警、Runbook | 生产阻断 |
| 回滚方案不可执行 | 发布演练 | P0 | 补回滚脚本与验证 | 是 |
| 交接命令不可复现 | 后续 Agent 复跑 | P1 | 修正 README / Runbook | 视阶段 |

### 7.2 验收失败后的处理流程

```text
门禁失败
→ 自动创建 KnownIssue
→ 判定 P0/P1/P2/P3
→ 指派 Owner
→ 关联模块与文档
→ 修复代码/配置/文档/Prompt
→ 执行回归测试
→ 更新证据
→ 重新复核门禁
→ 更新最终决策
```

规则：

1. P0 不得通过口头承诺关闭。
2. P1 必须有明确 workaround 和修复日期。
3. P2/P3 必须进入迭代池，不能丢失。
4. 所有失败修复都必须绑定 Commit、测试结果和证据项。
5. 涉及积分、订单、用户资产、合规投诉的修复必须保留审计日志。

### 7.3 发布后异常与回滚

触发 Rollback 的条件：

1. 主链路任务成功率显著低于上线门槛。
2. 积分重复扣除、错误扣费或大面积返还失败。
3. 生成内容出现高风险侵权、仿脸、仿声、洗稿、未授权复用并已影响用户。
4. 用户资产越权访问或数据删除失败。
5. 任务队列积压导致大量卡死且补偿失败。
6. 模型供应商异常导致成本失控或输出质量不可控。
7. 支付回调异常导致订单状态错乱。
8. 合规负责人或项目 Owner 要求紧急下线。

回滚步骤：

```text
触发告警
→ 值班负责人确认
→ 关闭相关 Feature Flag
→ 暂停高风险任务创建
→ 保留现有任务状态和资产
→ 执行代码/配置/Prompt 回滚
→ 执行数据库兼容回滚或前滚修复
→ 处理积分返还和用户通知
→ 生成事故记录
→ 复盘后重新进入验收流程
```

### 7.4 AI 能力失败回退

| 失败点 | 回退策略 |
|---|---|
| Content DNA 生成失败 | 重试一次 → 更换模型 → 降级输出部分报告 → 失败返还未消耗积分 |
| Creative IR 生成失败 | 使用上一个合格 Content DNA 重新生成 → 降低输出数量 → 转人工复核 |
| 脚本/标题/封面/Prompt 输出失败 | 分项重试；部分成功则部分扣费；失败项返还 |
| 风控误杀 | 允许用户申诉 → 人工复核 → 放行/重写/返还 |
| 风控漏判 | 立即下架相关输出 → 补充样本 → Prompt/规则回归 → 通知用户 |
| Benchmark 下降 | 禁止 Prompt/模型版本发布 → 回滚上个版本 |

## 8. 风控与合规

### 8.1 D24 合规验收原则

D24 的合规验收不是“检查有没有免责声明”，而是检查合规是否进入了产品流程、数据结构、API、任务队列、Prompt、后台、日志、测试和运营 SOP。

必须满足：

1. 用户上传或输入对标内容前，必须完成授权确认。
2. 系统必须明确禁止搬运、克隆、洗稿、仿脸、仿声、未授权素材复用。
3. AI 输出必须经过质检和相似度风控。
4. 高风险内容必须可拦截、可重写、可人工复核。
5. 所有 AIGC 输出和导出内容必须提供标识说明。
6. 投诉删除必须可执行、可审计、可通知。
7. 后台访问用户资产必须受权限控制和审计。
8. 用户数据删除必须覆盖派生资产、导出文件和可清理日志。
9. 模型供应商调用必须记录数据传输和成本。
10. 合规、安全、计费 P0 不允许通过“上线后补”解决。

### 8.2 风险分级与最终验收动作

| 风险等级 | 示例 | 验收动作 |
|---|---|---|
| R0 低风险 | 普通原创脚本、标题、封面建议，无敏感内容 | 可放行，记录日志 |
| R1 提示风险 | 内容可能过度标题党、行业表达不严谨 | 用户提示或自动优化 |
| R2 中风险 | 输出与原视频结构/表达过近，存在轻度虚假宣传 | 自动重写或要求用户编辑 |
| R3 高风险 | 疑似侵权、肖像、声音、商标、未授权素材复用 | 人工复核，未通过不得导出 |
| R4 禁止风险 | 仿脸、仿声、搬运、洗稿、规避平台审核、违法违规 | 直接拦截，必要时限制账号并返还未消耗积分 |

D24 验收时，必须用红队样本验证 R3/R4 是否能被识别和处理。

### 8.3 人工复核验收

人工复核必须具备：

1. 复核入口。
2. 证据包展示。
3. 原始输入、Content DNA、Creative IR、输出包、风控报告。
4. 用户授权记录。
5. 模型调用和 Prompt 版本。
6. 决策按钮：放行、要求重写、要求补充授权、拒绝、删除。
7. 用户通知模板。
8. 积分冻结/扣费/返还联动。
9. 审计日志。
10. 复核 SLA 和超时处理。

### 8.4 投诉删除验收

投诉删除流程必须支持：

```text
用户/权利人/平台投诉
→ 创建工单
→ 初筛投诉类型
→ 暂停展示高风险资产
→ 聚合证据包
→ 合规复核
→ 删除或保留决策
→ 删除原始和派生资产
→ 积分/退款/补偿处理
→ 用户或投诉方通知
→ 审计记录
→ 风控样本回写
```

验收标准：

- 能定位任务、资产、输出、导出文件和派生数据。
- 能执行软删除和必要的硬删除/对象存储清理。
- 能保留必要审计证据，但不得继续公开展示侵权风险资产。
- 能触发用户通知和客服 SOP。
- 能把事件回写到风控样本和 Prompt 回归。

### 8.5 数据安全与权限验收

D24 必须确认：

1. 普通用户只能访问自己的任务、资产、报告和积分。
2. 组织成员只能访问授权范围内的数据。
3. 后台客服默认不能查看原始视频和敏感 Prompt，除非工单需要且具备权限。
4. 风控复核员可以查看风险证据包，但操作必须审计。
5. 管理员操作必须记录 AuditLog。
6. 对象存储文件必须使用签名 URL 或受控访问。
7. 日志中不得裸露 API Key、支付密钥、用户敏感信息和完整商业机密。
8. 数据删除必须覆盖原始资产、抽帧、音频、ASR/OCR、Content DNA、Creative IR、导出文件等可删除资产。

# 附录 C：D24 版本治理规则

2. 任何影响 D16 数据库/API 的变更必须先生成迁移设计和兼容策略。
