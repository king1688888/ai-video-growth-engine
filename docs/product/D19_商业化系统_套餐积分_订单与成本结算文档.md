## 2. 文档目标

### 2.1 本文档要解决的问题

D19 要解决的是 MVP1 从「能生成内容」升级为「能真实收费、可控成本、可核算毛利、可处理失败争议」的问题。AI 视频理解和原创脚本生成是高成本长任务，如果没有商业化系统，项目会出现以下风险：

1. 用户能免费大量调用高成本模型，导致毛利失控。
2. 任务失败后积分扣错，造成投诉和退款压力。
3. 模型成本只在供应商后台可见，无法按任务、用户、功能、模型核算。
4. 支付订单、积分账户、任务状态、模型调用日志互相脱节。
5. 后台无法判断某个任务到底赚了还是亏了。
6. 用户取消、风控拦截、模型超时、部分成功时没有一致结算规则。
7. 客服无法人工补偿，或者补偿没有审计日志。
8. 订阅套餐权益、免费额度、积分包、企业共享额度混在一起，后续扩展困难。
9. AIcoding Agent 只做价格页和假支付按钮，不能支撑真实商业上线。
10. 企业客户需要账单、成员、额度、发票、成本明细时系统无法支持。

D19 必须把以下商业化链路工程化：

```text
价格页 / 套餐配置
→ 注册赠送免费额度
→ 用户购买积分包或订阅
→ 订单创建
→ 支付回调
→ 积分入账 / 权益生效
→ 用户创建视频拆解任务
→ 任务报价
→ 积分冻结
→ 任务执行并记录模型成本
→ 成功扣费 / 部分成功结算 / 失败返还
→ 用户账单与后台成本统计
→ 退款 / 人工补偿 / 投诉删除联动
→ 毛利看板与成本预警
```

## 4. 核心结论

### 4.1 MVP1 商业化原则

MVP1 商业化必须优先采用「积分账户 + 任务冻结 + 成功结算 + 失败返还」模型，而不是任务创建时直接不可逆扣费。

推荐主流程：

```text
任务创建
→ 风险预检
→ 生成报价 BillingQuote
→ 校验余额与套餐权益
→ 冻结积分 CreditHold
→ 入队执行
→ 模型调用记录 ModelCallLog
→ 成本入账 CostLedgerEntry
→ 风控质检
→ 任务成功：正式扣除积分
→ 任务失败：释放或返还积分
→ 部分成功：按可交付物结算，剩余返还
→ 后台展示任务收入、成本、毛利、失败原因
```

### 4.2 MVP1 计费对象

MVP1 不按「模型 token」直接向用户计费，而按用户能理解的交付物和工作流计费：

| 计费对象 | MVP1 是否计费 | 说明 |
|---|---:|---|
| 视频上传与文件校验 | 否 / 低成本包含 | 免费额度可覆盖，避免用户刚上传就被扣费 |
| 视频处理证据包 | 是 | 抽帧、ASR、OCR、镜头切分、证据包构建 |
| Content DNA | 是 | 核心价值项 |
| 拆解报告 | 是 | 生成可读报告 |
| Creative IR | 是 | 原创化中间层 |
| 原创脚本 | 是 | 默认 5 条 |
| 标题 | 是 | 默认 10 条 |
| 封面建议 | 是 | 默认 3 条 |
| 视频生成 Prompt | 是 | 默认 3 条 |
| 风控质检 | 包含 | 不能作为用户可关闭的付费项 |
| 导出报告 | P0 可免费 1 次，P1 可计费 | 免费版限制导出或带水印 |
| 完整视频生成 | MVP1 不做 | 仅预留未来高成本计费项 |
| 自动发布 | MVP1 不做 | 不进入商业化主流程 |

### 4.3 MVP1 最小套餐建议

> 具体价格由项目 Owner 最终确认，D19 只定义结构与可配置能力。所有金额、积分数量、权益次数必须从后台配置读取，不允许硬编码。

| 套餐 | 适用对象 | 权益 | 计费方式 | MVP1 建议 |
|---|---|---|---|---|
| 免费体验 | 新用户 | 注册赠送少量积分，支持 1 次轻量拆解或样例报告 | 免费额度 | P0 |
| 积分包 | 低频用户 / 本地商家 | 购买固定积分，按任务消耗 | 一次性订单 | P0 |
| 创作者订阅 | 高频个人用户 | 每月积分额度 + 高级导出 + Prompt 输出 | 月/年订阅 | P1 |
| 团队订阅 | 小团队 / MCN | 多成员、共享积分池、后台统计 | 订阅 + 超额积分 | P1/P2 |
| 企业套餐 | 企业 IP / 连锁商家 | 合同账单、共享额度、人工支持、专属模板 | 合同制 | 预留 |

### 4.4 积分价值原则

积分不是虚拟资产交易系统，而是平台内部的 AI 服务用量单位。积分需要满足：

1. **可解释**：用户知道一次任务大概消耗多少积分。
2. **可预测**：任务开始前必须报价并冻结积分。
3. **可追溯**：每一笔积分变动都有 `CreditTransaction`。
4. **可补偿**：失败、取消、风控拦截、客服补偿可返还。
5. **可审计**：后台能看到来源、用途、关联任务、操作人、原因。
6. **可控成本**：积分消耗需要覆盖模型成本、存储成本、失败重试成本和毛利目标。
7. **不可绕风控**：付费不能解锁侵权、搬运、仿脸、仿声、高相似复制等禁止能力。

### 4.5 成本核算原则

商业化系统必须区分三类账：

| 账目 | 含义 | 事实来源 |
|---|---|---|
| 用户积分账 | 用户冻结、扣除、返还、补偿的积分流水 | `credit_transactions` / `credit_holds` |
| 订单支付账 | 用户付款、退款、订阅、发票、支付回调 | `orders` / `payments` / `refunds` |
| 模型成本账 | 实际供应商调用、处理、存储、失败重试成本 | `model_call_logs` / `cost_ledger_entries` |

毛利不能用「收款 - 估算成本」粗略代替，必须按任务、用户、模型、功能维度聚合：

```text
任务毛利 = 任务收入折算金额 - 任务模型成本 - 存储/带宽估算成本 - 支付通道成本 - 退款/补偿成本分摊
```

### 4.6 商业化上线最低标准

D19 认为商业化上线必须至少满足：

1. 用户可以看到价格页或积分说明。
2. 用户可以查询积分余额、冻结积分、历史消耗。
3. 系统能创建订单，并正确处理支付成功/失败/取消/重复回调。
4. 任务创建前有报价。
5. 任务执行前冻结积分。
6. 同一任务不会重复扣费。
7. 任务失败能按规则释放或返还积分。
8. 任务取消能按成本状态结算。
9. 模型调用成本能按任务记录。
10. 后台能查看收入、成本、毛利、失败返还、人工补偿。
11. 客服能在权限控制下人工补偿，且必须写审计日志。
12. 风控拦截、人工复核、投诉删除能联动计费状态。
13. 支付密钥、Webhook Secret、用户账单信息不能暴露到前端或日志。
14. 所有商业化核心状态有自动化测试覆盖。

### 5.2 用户商业化主流程

```text
用户注册 / 登录
→ 系统创建 billing_account 与 credit_account
→ 发放注册赠送积分 / 免费额度
→ 用户进入价格页或工作台
→ 用户上传视频并创建任务
→ 系统基于视频长度、输出包、质量模式、用户套餐生成 BillingQuote
→ 校验积分余额和用量限制
→ 用户确认授权、风险提示、积分冻结
→ 系统创建 CreditHold
→ 任务进入 D17 队列执行
→ 每次模型调用记录 ModelCallLog 和 CostLedgerEntry
→ 任务完成并通过风控
→ 系统根据可交付物生成 UsageRecord
→ CreditHold 转为正式扣费 CreditTransaction
→ 报告可查看/导出
→ 后台可查看本任务收入、成本、毛利
```

### 5.3 任务计费状态机

| 状态 | 含义 | 进入条件 | 可执行动作 |
|---|---|---|---|
| `not_quoted` | 尚未报价 | 任务刚创建 | 生成报价 |
| `quoted` | 已报价未冻结 | 报价成功 | 用户确认 / 重新报价 / 取消 |
| `hold_pending` | 冻结处理中 | 用户确认开始任务 | 创建冻结 |
| `held` | 积分已冻结 | 冻结成功 | 入队执行 |
| `settlement_pending` | 等待结算 | 任务完成/失败/取消/风控 | 结算扣费或释放 |
| `charged` | 已正式扣费 | 任务成功且交付物可用 | 查看账单 |
| `partially_charged` | 部分扣费 | 部分交付成功 | 返还剩余冻结 |
| `released` | 已释放冻结 | 未执行或失败无成本 | 账单记录 |
| `refunded` | 已返还 | 已扣费后发生可退款事件 | 查看退款/补偿 |
| `manual_review` | 人工复核 | 金额异常/风控争议/用户投诉 | 人工处理 |
| `settlement_failed` | 结算失败 | 数据缺失/并发冲突/状态异常 | 重试 / 人工修复 |

### 5.4 计费时机与扣费规则

| 场景 | 是否冻结 | 是否扣费 | 返还规则 |
|---|---:|---:|---|
| 用户创建任务但未确认 | 否 | 否 | 无需返还 |
| 用户确认后任务未开始 | 是 | 否 | 取消时全额释放 |
| 文件校验失败 | 否或释放 | 否 | 全额释放 |
| 风险预检拦截，未调用高成本模型 | 否或释放 | 否 | 全额释放 |
| 视频处理失败，未生成可用证据包 | 是 | 否或低成本扣除 | MVP1 默认全额释放，后续可按成本扣除 |
| 模型调用失败且无可用输出 | 是 | 否 | 全额或按已消耗成本部分扣除，P0 建议全额释放 |
| Content DNA 成功但输出包失败 | 是 | 部分扣费 | 按成功交付物结算，剩余释放 |
| 风控后置拦截，需要强制重构 | 是 | 暂不正式扣费 | 自动重写一次；仍失败则释放或转人工 |
| 人工复核中 | 是 | 暂不正式扣费 | 审核通过扣费，不通过释放 |
| 用户主动取消且模型未调用 | 是 | 否 | 全额释放 |
| 用户主动取消但模型已调用 | 是 | 部分扣费 | 按已产生的不可撤销成本扣除，剩余释放 |
| 任务成功 | 是 | 是 | 正式扣除报价内积分 |
| 用户投诉成立 | 已扣费 | 返还或补偿 | 按客服 SOP 退积分/退款/补偿 |
| 系统重复扣费 | 已扣费 | 纠错 | 立即返还重复扣费并记录事故 |

### 5.6 积分账户设计

#### 5.6.1 积分类别

| 类型 | 说明 | 过期规则 | 消耗优先级 |
|---|---|---|---|
| `free_trial` | 注册/活动赠送 | 短周期过期 | 优先消耗 |
| `subscription_grant` | 订阅周期发放 | 周期结束失效或顺延，按配置 | 次优先 |
| `purchased` | 积分包购买 | 较长有效期 | 中优先 |
| `bonus` | 活动赠送 | 按活动规则 | 低优先 |
| `compensation` | 客服补偿 | 不短于原积分有效期 | 高优先或按策略 |
| `enterprise_pool` | 企业共享池 | 合同配置 | 按组织策略 |

#### 5.6.2 积分消耗优先级

默认推荐：

```text
即将过期积分
→ free_trial
→ compensation
→ subscription_grant
→ bonus
→ purchased
→ enterprise_pool
```

后台必须可配置优先级，但每次消耗必须在 `CreditTransaction.metadata` 中记录消耗明细，避免用户对「为什么先扣哪个积分」产生争议。

#### 5.6.3 积分冻结

积分冻结不是扣费。冻结用于防止用户在任务执行过程中余额被其他任务消耗，导致任务完成后无法结算。

冻结规则：

1. 创建任务报价后，用户确认才冻结。
2. 冻结金额 = 预计最高扣费金额 + 安全缓冲；MVP1 可不加缓冲。
3. 冻结必须有过期时间，防止任务卡死长期占用积分。
4. 冻结必须绑定 `task_id`、`quote_id`、`user_id`、`idempotency_key`。
5. 冻结成功后任务才可进入高成本队列。
6. 同一任务只能有一个 active 冻结。
7. 任务终态必须触发冻结结算或释放。

#### 5.8.4 支付渠道适配原则

1. 支付服务商必须通过 `PaymentProviderAdapter` 接入。
2. 前端不能接触支付密钥。
3. 支付 Webhook 必须校验签名。
4. Webhook 处理必须幂等。
5. 支付成功不等于权益发放成功，必须有 `fulfillment_pending` 状态。
6. 支付成功但权益发放失败必须进入补偿队列。
7. 订单金额、币种、商品、用户必须在回调时二次校验。
8. 支付失败不能创建积分流水。
9. 支付敏感信息不得写入普通日志。
10. 支付供应商选择待项目 Owner 确认，MVP1 可先用 Stripe / Lemon Squeezy / Paddle / 支付宝 / 微信支付中的一种或 Mock Provider，但生产必须真实接入并标记环境。

### 5.10 退款与补偿设计

#### 5.10.1 退款类型

| 类型 | 场景 | 处理方式 |
|---|---|---|
| `system_failure_refund` | 系统故障导致任务失败 | 自动返积分或退款 |
| `model_failure_refund` | 模型失败无可用输出 | 自动返积分 |
| `duplicate_charge_refund` | 重复扣费 | 自动返积分，严重时退款 |
| `risk_block_release` | 风控前置拦截 | 释放冻结或返还 |
| `quality_complaint_compensation` | 输出质量投诉，经人工确认 | 人工补偿积分 |
| `legal_complaint_refund` | 权利人投诉/合规处理 | 结合 D21/D22 SOP |
| `subscription_refund` | 订阅退款 | 按支付渠道和协议 |
| `chargeback_loss` | 支付拒付 | 冻结账户并进入风控 |

#### 5.10.2 返还优先级

默认推荐：

1. 未正式扣费：释放冻结。
2. 已扣积分但未支付现金：返还积分。
3. 积分包购买后任务失败：优先返还积分，不直接现金退款。
4. 订阅周期内任务失败：返还积分或补偿额度。
5. 支付错误、重复收款、法律强制退款：现金退款。
6. 企业合同客户：按合同 SLA 和账期处理。

#### 5.10.3 人工补偿约束

人工补偿必须满足：

1. 只有具备 `billing_admin` 或 `support_lead` 权限的人员可操作。
2. 补偿必须选择原因码。
3. 单次补偿超过阈值需要二次审批。
4. 补偿必须写入 `manual_credit_adjustments`、`credit_transactions`、`audit_logs`。
5. 补偿不得用于绕过风控生成高风险内容。
6. 后台必须能按客服、用户、原因、金额统计补偿。

## 6.6 AI Prompt 设计

D19 的核心计费、扣费、返还、订单状态必须由确定性代码和账本规则执行，不允许由 LLM 决定。D19 只允许在以下非决策场景使用 AI：

1. 成本异常归因摘要。
2. 客服退款/补偿建议草稿。
3. 用户账单解释文案生成。
4. 后台毛利下降分析摘要。

AI 输出只能作为「辅助说明」，不得直接修改余额、订单、退款、风控结果。

### 6.6.1 Prompt：成本异常归因摘要

**Prompt ID**：`P19_COST_ANOMALY_SUMMARY`  
**用途**：将结构化成本异常数据整理成后台可读摘要，帮助运营/技术排查。  
**调用时机**：`billing.anomaly.detect` 产生异常后。  
**是否影响扣费**：否。

#### 输入 Schema

```json
{
  "anomaly_event": {
    "event_id": "string",
    "severity": "low|medium|high|critical",
    "event_type": "cost_spike|margin_drop|retry_cost_high|free_user_cost_high|provider_price_mismatch",
    "task_id": "string",
    "user_id": "string",
    "feature_key": "string",
    "model_provider": "string",
    "model_name": "string",
    "detected_value": "number",
    "threshold_value": "number",
    "time_window": "string"
  },
  "related_records": {
    "billing_quote": {},
    "model_call_logs": [],
    "cost_ledger_entries": [],
    "task_step_logs": [],
    "risk_check_report": {}
  }
}
```

#### 输出 Schema

```json
{
  "summary": "string",
  "likely_causes": [
    {
      "cause": "string",
      "confidence": 0.0,
      "evidence": ["string"]
    }
  ],
  "recommended_actions": [
    {
      "action": "string",
      "owner_role": "billing_admin|ai_engineer|devops|support",
      "priority": "low|medium|high"
    }
  ],
  "requires_manual_review": true,
  "do_not_auto_refund": true
}
```

#### Prompt 模板

```text
你是本项目的商业化成本分析助手。你只能基于输入的结构化账务、模型调用、任务日志和风控记录生成后台排查摘要。

硬性规则：
1. 不得编造不存在的订单、成本、模型调用或退款事实。
2. 不得决定是否扣费、退款、返积分。
3. 不得输出用户可见的法律或财税结论。
4. 不得建议绕过风控、关闭合规审核或删除审计日志。
5. 如果证据不足，必须输出“证据不足，需要人工排查”。

请根据输入 JSON 输出符合指定 JSON Schema 的中文结果。
```

#### 评测标准

| 指标 | 通过标准 |
|---|---|
| Schema 合法率 | 100% |
| 不编造事实 | 人工抽检通过率 ≥ 98% |
| 原因可追溯 | 每个原因必须有 evidence |
| 不越权决策 | 不得输出自动退款/扣费命令 |
| 可读性 | 后台运营能理解并执行 |

#### 失败回退

1. JSON 解析失败：执行 JSON repair 一次。
2. 仍失败：保存原始异常，后台显示「AI 摘要失败」。
3. 不影响告警、不影响账务、不影响退款。
4. 高危异常直接人工复核，不依赖 AI 摘要。

### 6.6.2 Prompt：客服补偿建议草稿

**Prompt ID**：`P19_SUPPORT_COMPENSATION_DRAFT`  
**用途**：辅助客服基于任务状态、失败原因、用户历史生成补偿建议。  
**是否自动执行补偿**：否，必须人工确认。

输出必须包含：

1. 事件摘要。
2. 用户是否符合补偿候选。
3. 建议补偿类型：无 / 返还冻结 / 返积分 / 赠送补偿积分 / 现金退款候选。
4. 风险提示：是否存在滥用、重复投诉、合规投诉。
5. 建议客服话术草稿。

硬性限制：

1. 不得直接创建退款。
2. 不得承诺法律责任。
3. 不得承诺平台流量效果。
4. 不得建议补偿高风险违规需求。
5. 高金额或法律投诉必须转人工主管。

## 7. 异常与失败处理

### 7.1 订单异常

| 异常 | 处理策略 | 日志 |
|---|---|---|
| 订单创建重复 | 使用 `idempotency_key` 返回已有订单 | `billing_audit_logs` |
| 支付成功但订单未更新 | Webhook 重试 + 对账任务修复 | `payment_webhook_events` |
| 支付成功但积分未到账 | 进入 `fulfillment_pending`，补偿队列发放 | `billing.payment.fulfill` |
| 支付金额不匹配 | 标记 `manual_review`，不发放权益 | `billing_anomaly_events` |
| 支付币种不匹配 | 拒绝处理，人工复核 | `billing_anomaly_events` |
| Webhook 签名无效 | 拒绝处理，高危告警 | 安全日志 |
| 支付渠道超时 | 用户可重试，订单保持 `pending_payment` | API 日志 |
| 支付拒付/Chargeback | 冻结相关权益，进入风控复核 | 审计日志 |

### 7.2 积分异常

| 异常 | 处理策略 |
|---|---|
| 积分余额不足 | 阻止任务执行，提示充值或轻量模式 |
| 冻结失败 | 不入队高成本任务 |
| 冻结过期 | 自动释放，任务若仍运行则进入异常 |
| 重复冻结 | 幂等返回已有 active hold |
| 重复扣费 | 自动识别并返还重复部分 |
| 负余额 | 阻断用户新任务，进入账务修复 |
| 积分批次过期争议 | 依据 `credit_lots` 与配置展示解释 |
| 人工补偿超限 | 二次审批 |
| 返还失败 | 补偿队列重试，仍失败则人工处理 |

### 7.3 任务结算异常

| 异常 | 处理策略 |
|---|---|
| 任务成功但无报价 | 不自动扣费，进入人工复核 |
| 任务成功但无冻结 | 不自动扣费，进入人工复核 |
| 成本日志缺失 | 可先按报价扣费，但标记成本缺失异常；P0 可进入人工复核 |
| 任务失败但冻结未释放 | 定时扫描释放 |
| 部分成功无交付物明细 | 按失败处理释放，避免争议 |
| 风控拦截但已扣费 | 自动返还或人工补偿 |
| 结算队列失败 | 重试 3 次后进入死信和后台告警 |
| 用户取消与任务完成并发 | 以任务终态时间和模型调用状态为准，幂等结算 |

### 7.4 成本异常

| 异常 | 处理策略 |
|---|---|
| 单任务成本超过报价收入 | 标记低毛利，后台告警，后续调整价格或路由 |
| 免费用户成本过高 | 限制免费额度、降级模型、要求验证 |
| 模型价格配置缺失 | 阻止高成本调用或使用保守估价 |
| 供应商价格变化 | 更新 `model_catalog` 与 `pricing_rules`，触发回归 |
| 重试成本过高 | 触发重试熔断 |
| 成本币种不一致 | 使用汇率配置快照，不实时浮动 |
| 成本日志重复 | 通过 `source_id + task_step + model_call_id` 去重 |

### 7.5 退款与投诉异常

| 异常 | 处理策略 |
|---|---|
| 用户申请退款但积分已消耗 | 按订单规则计算可退余额，必要时人工处理 |
| 用户投诉输出不可用 | 先走质量复核，不直接退款 |
| 权利人投诉 | 立即冻结相关资产与导出，进入 D21/D22 流程 |
| 用户滥用退款 | 标记风控，限制补偿 |
| 客服错误补偿 | 需要反向调整并记录审批 |
| 现金退款失败 | 支付服务商重试，人工跟进 |
| 退款后仍保留权益 | 补偿队列撤销权益或冻结账户 |

## 8. 风控与合规

### 8.1 商业化不能绕过合规

付费用户、企业用户、高价套餐均不能绕过以下底线：

1. 不支持搬运、克隆、洗稿、仿脸、仿声。
2. 不支持未授权素材复用。
3. 不支持规避平台风控。
4. 不支持高相似复制对标视频。
5. 不支持虚假宣传、违法违规、高风险医疗金融法律结论性内容。
6. 高风险内容必须走风控拦截、强制重构或人工复核。
7. 风控拦截不能通过额外付费解锁。

### 8.2 授权确认与计费关系

任务冻结积分前，用户必须完成：

1. 上传素材授权确认。
2. 对标内容使用边界确认。
3. 原创化生成确认。
4. AIGC 标识/平台规则提示确认。
5. 失败返还和计费规则确认。

如果用户未确认授权，系统不得冻结积分，不得进入高成本队列。

### 8.3 AIGC 标识与账单

商业化系统应记录以下字段：

1. 任务是否涉及 AIGC 输出。
2. 导出报告是否包含 AIGC 标识提示。
3. 用户是否确认平台发布需自行遵守 AIGC 标识要求。
4. 企业套餐是否需要默认开启 AIGC 标识提醒。
5. 因 AIGC 标识投诉导致的退款/补偿，需要进入人工复核。

### 8.4 风险分级对计费的影响

| 风险等级 | 计费动作 |
|---|---|
| `low` | 正常报价、冻结、结算 |
| `medium` | 正常报价，但展示风险提示；部分输出可能需重构 |
| `high` | 不进入自动扣费完成态；需自动重写或人工复核 |
| `blocked` | 不执行高成本任务；释放冻结或不冻结 |
| `legal_complaint` | 冻结资产与相关账务操作，人工处理 |
| `abuse_suspected` | 限制免费额度、暂停补偿或支付权益发放 |

### 8.5 人工复核

以下情况必须进入人工复核：

1. 单任务费用或成本超过阈值。
2. 订单金额异常。
3. 重复退款或高频投诉用户。
4. 高风险行业请求。
5. 风控后置拦截但用户已付费。
6. 权利人投诉。
7. 企业客户大额补偿。
8. 支付拒付或欺诈风险。
9. 任务状态和计费状态不一致。
10. 后台人工调整超过权限阈值。

### 8.6 投诉删除机制与计费联动

当用户或权利人发起投诉删除：

1. 系统应冻结相关报告、导出文件和生成资产访问。
2. 保留必要审计日志和账务日志。
3. 如果投诉成立，按 D21/D22/D23 SOP 处理删除、返还、退款或补偿。
4. 删除内容不等于删除账务记录；账务记录需保留必要审计字段并做脱敏。
5. 投诉处理结果必须写入 `billing_audit_logs` 和 `manual_review_tickets`。
6. 因违规被删除的内容，不得通过重复购买重新生成相同高风险输出。

### 8.7 数据安全与权限

1. 支付密钥、Webhook Secret 不得入库明文、不得进入前端、不得提交 Git。
2. 不存储银行卡号等高敏支付信息，只保存支付服务商 token / ID / 状态。
3. 账单、订单、支付、退款信息属于高敏运营数据。
4. 普通客服只能查看必要订单状态，不得查看完整支付元数据。
5. 人工补偿必须二次审计。
6. 账务日志不可随意删除，只能按数据治理策略脱敏归档。
7. 用户导出账单只能导出自己的订单和积分流水。
8. 企业管理员只能查看所属组织账单。

## 9. 测试与验收标准

### 9.1 单元测试

| 测试对象 | 必测内容 |
|---|---|
| 报价引擎 | 不同视频长度、套餐、输出包、质量模式报价正确 |
| 积分账户 | 入账、冻结、扣费、释放、返还、过期 |
| 积分批次 | 消耗优先级、有效期、余额计算 |
| 订单状态机 | draft → pending → paid → fulfilled |
| 支付回调 | 签名校验、幂等处理、金额校验 |
| 结算引擎 | 成功扣费、失败释放、部分扣费 |
| 成本聚合 | ModelCallLog 到 CostLedgerEntry |
| 退款补偿 | 退款、返积分、人工补偿 |
| 权益校验 | 视频时长、任务频率、导出权限 |
| 异常检测 | 成本超阈值、重复扣费、负余额 |

### 9.2 API 测试

必须覆盖：

1. 未登录访问账单 API 被拒绝。
2. 用户不能查看他人订单。
3. 套餐列表可公开访问但不暴露后台成本。
4. 积分不足不能进入高成本队列。
5. 报价过期后不能冻结。
6. 同一 `idempotency_key` 多次创建订单返回同一订单。
7. 支付 Webhook 重复发送不重复发放积分。
8. 后台人工补偿需要权限。
9. 权限不足不能退款。
10. 账单分页、筛选、排序正确。

### 9.3 E2E 测试

MVP1 必须通过以下端到端用例：

1. 新用户注册 → 获得免费积分 → 创建轻量任务 → 冻结积分 → 任务成功 → 扣费 → 查看账单。
2. 用户购买积分包 → 支付成功 → 积分到账 → 创建标准任务 → 成功扣费。
3. 用户积分不足 → 创建任务报价 → 被提示充值或轻量模式。
4. 任务处理失败 → 自动释放冻结 → 用户看到返还记录。
5. 任务部分成功 → 部分扣费 → 剩余释放。
6. 用户取消未开始任务 → 全额释放。
7. 风控预检拦截 → 不扣费或释放冻结。
8. 支付 Webhook 重复回调 → 积分只到账一次。
9. 后台人工补偿 → 用户余额增加 → 审计日志可查。
10. 成本异常任务 → 后台告警出现。

### 9.4 并发与幂等测试

必须验证：

1. 同一任务同时触发两次结算，不会重复扣费。
2. 用户同时创建多个任务，冻结余额不会超支。
3. 支付成功回调与用户刷新订单页面并发，不会重复发放。
4. 任务取消与任务完成并发，只产生一个最终结算。
5. 积分释放任务重复执行，不会增加余额。
6. 退款任务重复执行，不会重复退款。
7. 结算 Worker 崩溃后重启可恢复。

### 9.5 成本与毛利验收

| 指标 | MVP1 验收标准 |
|---|---|
| 单任务成本记录覆盖率 | ≥ 99% |
| ModelCallLog 与 CostLedger 对齐率 | ≥ 99% |
| 重复扣费率 | 0 |
| 失败返还成功率 | ≥ 99% |
| 支付回调幂等成功率 | 100% |
| 免费用户单日成本上限 | 可配置且生效 |
| 成本异常告警延迟 | P0 可 10 分钟内，P1 可实时 |
| 后台毛利统计 | 至少支持日维度、任务维度、模型维度 |
| 高成本任务拦截 | 超阈值任务必须阻断或人工复核 |

### 9.6 风控合规验收

1. 高风险内容不能通过付费解锁。
2. 未授权确认不能冻结积分。
3. 风控拦截后的冻结必须释放或转人工。
4. 投诉删除后导出文件不可继续访问。
5. 账务审计日志可追踪。
6. 人工补偿必须记录操作人、原因、前后余额。
7. 支付密钥不出现在前端包、日志、Git 历史。
8. 用户不能访问他人账单。
9. 企业成员不能越权查看其他组织账单。
10. Mock 支付不能在生产环境开启。

### 9.7 上线阻断项

出现以下任一情况，不允许商业化上线：

1. 任务可能重复扣费。
2. 任务失败不返还或返还无记录。
3. 支付回调未校验签名。
4. 支付成功可能重复发放积分。
5. 后台可无权限补偿积分。
6. 成本无法按任务记录。
7. 生产环境使用 Mock 支付且未明确标识。
8. 用户可越权查看他人订单。
9. 积分余额可出现无原因负数。
10. 风控拦截后仍自动扣费。
11. 密钥写入前端或 Git。
12. 无任何账务审计日志。

## 12. 不做事项

MVP1 D19 明确不做：

1. 不做完整财务 ERP。
2. 不做复杂税务自动化和正式电子发票全链路，仅做发票申请预留。
3. 不做多币种实时汇率结算，P0 默认单币种配置。
4. 不做自研支付网关，只接第三方支付服务商。
5. 不存储银行卡号、CVV 等高敏支付信息。
6. 不做积分交易市场、积分转让、积分提现。
7. 不做加密货币支付。
8. 不做动态竞价或复杂实时成本加价算法。
9. 不做用户绕过风控的付费解锁。
10. 不做完整视频生成的高成本计费，MVP1 仅预留。
11. 不做自动发布扣费。
12. 不做账号级批量抓取扣费。
13. 不做复杂渠道分销、代理商结算。
14. 不做全量企业合同账单自动化，P1/P2 再做。
15. 不做没有审计日志的后台手工改余额。
16. 不做任务创建即不可逆扣费。
17. 不做成本无法追溯到任务的总账式统计。
18. 不做生产环境无标识 Mock 支付。
19. 不做通过付费降低原创化强度或关闭合规审核。
20. 不做未授权素材、仿脸仿声、搬运复刻相关商业化包装。
