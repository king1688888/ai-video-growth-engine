# 迭代治理总政策

> Authority: D24, D20, D23  
> 日期: 2026-05-26

---

## 核心原则

任何上线后的变更都必须经过：**评估 → 测试 → 审批 → 发布 → 监控 → 回滚预案**。

## 变更分级

| 级别 | 定义 | 审批 | 测试要求 | 发布方式 |
|------|------|------|----------|----------|
| L1 紧急修复 | 积分重复扣费/数据泄露/风控失效 | Owner 口头 + 事后补 PR | 最小回归 | 立即发布 |
| L2 普通修复 | Bug 修复/性能优化 | PR Review | 单测 + 相关集成测试 | 正常发布 |
| L3 Prompt/模型变更 | Prompt 文本/模型切换/参数调整 | PR Review + Benchmark | D12 Benchmark + 红队 | 灰度发布 |
| L4 功能变更 | 新功能/流程变更 | PR Review + 影响评估 | 全套测试 | 灰度 + Feature Flag |
| L5 架构变更 | DB Schema/API 契约/状态机 | ContractChangeRequest + Owner | 全套 + 迁移测试 | 分阶段发布 |

## 禁止事项

1. 不得将 MVP2+ 功能直接塞进 MVP1 生产主流程
2. 不得绕过 D00-D24 文档体系新增能力
3. 不得无 Benchmark 发布 Prompt 变更
4. 不得无幂等测试变更计费规则
5. 不得无红队测试变更风控阈值
6. 不得无回滚方案发布任何变更

## 变更流程

```text
1. 提交变更申请（Issue/PR）
2. 影响评估（DB/API/Queue/Prompt/Risk/Cost/Test）
3. 实现 + 测试
4. PR Review（含 Benchmark 结果）
5. Staging 验证
6. 灰度发布（5% → 20% → 50% → 100%）
7. 监控观察（24h）
8. 确认或回滚
```

---

*本政策适用于 MVP1 上线后的所有变更。*
